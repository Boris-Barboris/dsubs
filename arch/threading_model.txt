I'd like to make sure I utilize modern CPU capabilities.

Window events should be polled in their own thread, not bound to rendering
pipeline. It will make sure that stutter or unstable fps will not impact gameplay.
This also means, that user input is concurrent to representation of the game world.
There will also be a thread that listens for messages coming from the server.

Why do we need to correctly handle concurrency?
Dirty reads. No other reasons in game engine. Reads are only performed by
render thread. I think there is only one resource, that is subject to concurrent
writes from multiple threads: API unit buffer, that may recieve messages from
multiple windows - hence multiple event polling threads.

Let's define synchronization strategies:

stage-wide locking:
    window has a mutex, wich is held by render thread when it's issuing
    rendering commands. Effectively makes data update process serialized,
    but still allows parallel processing inside the stage. Render is
    free to distribute work to the thread pool.
    Problem is, if there are multiple windows, this scheme crumbles.

Component system-wide:
    For example, each window has it's own GUI lock. Problem emerges, when GUI
    controls start manipulating state other that GUI, wich well may be global,
    for example client-side world objects. And the most complex case is event,
    recieved from the server.
    Let's try this.

Lock everything:
    Lock every mutable object on read or write. Deadlock-heavy approach, since
    there is a lot of object indirection.

All single-threaded:
    Simple, but I want to git gud.

Manual consideration of what and where to lock:
    Most laboursome, but reliable and will work. It is very hard to
    add new code to such system.
